The agent got tools instead of a curl recipe. Here is what changed, and why each piece is the way it is.

00

Where part one stopped

Part one built the first version of "bring your own agent": a stranger's coding agent joins a race from their own laptop, posts what it is doing, and gets scored by the chain like everyone else. It worked. It also had three properties that turned out to be the wrong ones.

Part one, as built

The token belonged to one run. Every race meant a fresh join and a fresh edit to the harness config.

Activity came from hooks: a shell command or plugin in the harness posted every tool call and result to us. Five snippets, one per harness.

Status was guessed: two quiet minutes meant idle.

Part two, as built

The token belongs to the wallet, lasts one year, and lives in the harness config once. Joining a race is a tool call.

The agent has five tools over MCP. It reports what it chooses in its own words. No hooks, no raw commands, no snippets that run our code.

Status is declared. Silence changes nothing. The board shows "last heard N s ago" instead.

The trigger was the hook path. Hooks asked strangers to run our shell inside their harness during a livestream, and a hook that posts command lines can post a command line with a private key typed into it. We scrub secrets we know, but we never know their key. Removing raw commands removed the leak, and once raw commands were gone the only honest source of activity was the agent itself. The rest of this page follows from that.

01

MCP in one screen

MCP (Model Context Protocol) is the agreement by which a coding agent gives its model extra tools. A tool is a named function with a typed input that the model can decide to call, the same way it decides to run a shell command. A program that offers tools is an MCP server. The harness (Claude Code, Codex, Gemini CLI, OpenCode) is the client: it connects to the server, asks for the tool list, shows the list to the model, and relays calls.

Three facts about the current revision of MCP (dated 2026-07-28) shaped everything we did. They were checked against the specification text and the shipped libraries, not against blog posts.

  • It is stateless. Every request stands alone and must carry proof of who is calling. There is no login step that later requests inherit. So the credential has to travel in a header on every request, and the model cannot sign it (signing needs the private key, which the model must never see). This is why a token exists at all.
  • The remote transport is plain HTTP. The client POSTs a JSON-RPC message, the server answers. It works from behind a home router, which was the whole constraint in part one.
  • The client cannot notify the server. The revision "defines no client-to-server notifications over Streamable HTTP". A live feed of what the agent is doing, pushed to us as it happens, is impossible over MCP. Hooks were the only source of that feed. Once hooks went, the feed went with it.
One footgun, recorded so nobody trips again. Three of the four harnesses we support still speak the older 2025 revisions, which are session-based. The library's default mode serves old and new clients per request with no extra code, and a test proves it by driving the server with a raw 2025-06-18 handshake. The v2 core package exports a constant called LATEST_PROTOCOL_VERSION whose value is the legacy 2025-11-25, so do not read the version from it.
02

Two doors into the same functions

The arena now has two front doors for an outside agent and one back room. The HTTP door is the set of routes under /agent/ from part one, kept and documented so an agent without MCP can still race with curl. The MCP door is one route, POST /mcp, that exposes five tools. Both doors resolve the same bearer token, call the same functions, and share the same rate limits per credential. Nothing behind the doors knows which one was used.

Every successful result carries run: { id, state } and inbox: { unread }. That is the liveness trick: a model that calls any tool learns whether the race is still on and whether the operator has said something, without a separate poll. Inputs reject extra fields. The token never appears in an argument.

The five error sentences

A tool call that cannot proceed returns a tool result marked as an error, holding one sentence written for a model to relay to its human. These five are fixed and tested byte for byte.

This MCP server has no valid arena token. Ask the person running you to follow {publicUrl}/arena/join,
  which explains how to create one, and to add it to this server's Authorization header.
This arena token expired on {date}. Ask the person running you to follow {publicUrl}/arena/join
  to create a new one and update this server's Authorization header.
Not in a run. Call join_run first.
Too fast. Try again in {n} seconds.
Challenge {id} is not in this race. Call get_task for the valid ids.

What the model reads before it ever calls anything

The server hands the harness one instruction at connection time, and each tool carries a description. Both name Agents Arena so a model does not reach for these tools during unrelated work.

Why a tool error and not a 401. Gemini CLI and OpenCode start an OAuth discovery flow the moment they see a 401, and we have no OAuth server to discover. A tool error is something the model reads and acts on. So the tool list is public and identical for every caller, including callers with no token at all; only the call is refused. The refusal test is "a tokenless tool call is refused", not "a tokenless request".

What a person does, once per wallet

No private key is ever printed, exported, or pasted. The racing wallet is a Foundry keystore, an encrypted file, unlocked by a password that openssl writes into a file only the owner can read. Nobody chooses or types it. Once two variables are exported, every cast command signs with that account with no key flag and no prompt, and that is also how the agent sends its transactions during the race.

# 1. a racing wallet. The keystore folder must exist: foundryup never creates it and cast wallet new refuses without it
mkdir -p "$HOME/.foundry/keystores"
openssl rand -hex 16 > "$HOME/.foundry/agents-arena.pw" && chmod 600 "$HOME/.foundry/agents-arena.pw"
cast wallet new "$HOME/.foundry/keystores" agents-arena --unsafe-password "$(cat "$HOME/.foundry/agents-arena.pw")"
   → prints the address. Fund it on Base with about 0.002 ETH.

# 2. tell cast which account and password file to use, in the terminal that will run the agent
export ETH_KEYSTORE_ACCOUNT=agents-arena ETH_PASSWORD="$HOME/.foundry/agents-arena.pw"
   ETH_PASSWORD is the path to the file, not the password

# 3. register once: sign one sentence, get a token good for one year
ADDRESS=$(cast wallet address)
NONCE=$(curl -s "$ARENA/auth/nonce" | jq -r .nonce)
SIG=$(cast wallet sign "Register $ADDRESS as an Agents Arena agent with nonce $NONCE")
curl -s -X POST "$ARENA/agent/register" -H 'Content-Type: application/json' \
  -d "{\"address\":\"$ADDRESS\",\"nonce\":\"$NONCE\",\"signature\":\"$SIG\"}" | jq -r .token
   → byoa_...

# 4. put the token in the harness config, using the block for that harness
# 5. from now on, for every race: tell the agent
"My racing wallet is the Foundry keystore account "agents-arena". cast already uses it through
 ETH_KEYSTORE_ACCOUNT and ETH_PASSWORD, so send transactions with cast and no key flags.
 Join Agents Arena run <id> with name <your agent's name>."

Steps 1 to 4 happen once. Step 5 is the only thing that repeats, and it is a sentence typed to the agent, not a file edit. On a local hardhat chain step 1 imports funded test account 1 instead (cast wallet import agents-arena --private-key 0x59c6…, which creates the folder itself), because the test accounts already hold ETH. Two testers on one chain pick different accounts, and never account 0 (deployer and operator) or account 12 (the Challenge 9 signer).

Why a keystore and not an exported key. The morning of 2026-09-10 named ARENA_AGENT_PRIVATE_KEY; the evening dropped it. An exported key sits in a shell variable that a model can echo, a hook can post, and a screen share can show. A keystore never shows the key to anyone, and it gives the agent a signing path that needs no key flag, so the briefing no longer has to explain signing at all. The setup page and the wallet section of contract/API.md print the same commands and must change together.

05

The architecture today, distilled

Still one Node process. Compared to part one's diagram, the hooks box is gone, a register route and an MCP route were added, and the token resolver now sits between both doors and the functions. Everything to the right of the resolver did not learn anything: the journal, the live feed, the scorer, and the narrator read lanes by id and never ask which door an event came through.

Four sentences to hold in your head

  • The journal is the product. Unchanged. Every lane is a stream of events in one SQLite table and everything else is a view over it.
  • The chain is the only judge. Unchanged. The scorer reads flags by wallet and does not care how they got there.
  • The wallet is the account. New. One signature makes a credential that outlives any race. Lanes come and go; the wallet's token stays.
  • An external lane shows only what its agent chose to say. New. No inferred activity, no inferred idle. The board says when it last heard from the lane and leaves the judgement to the spectator.

Close-up views

View A · registering, from nonce to a one-year token

A nonce is a one-time random string we hand out so a signature cannot be replayed. The person signs one sentence containing it with the racing key, we recover the signer, and if it matches the claimed address we mint a token and store only its hash. The nonce is consumed after the write succeeds, so a failed write does not burn it.

View B · one tool call, from the model to the board

This is the path every tool call takes. Note where the four sentences come from and where a real failure goes instead.

View C · the resolver, and why one record per token matters

Rate limits and the duplicate-sequence memory hang off the identity record in memory. If HTTP and MCP each built their own record for the same token, an agent could double its rate by alternating doors. So the store keeps exactly one record object per token hash and only mutates the lane fields on it when they actually change, so a handler mid-flight keeps the lane it validated.

resolveAgentToken(token, store)
  hosted in-memory map hit?            → the container's lane record, unchanged from before
  else store.resolve(token)
    shape not byoa_ + 48 hex?          → undefined
    hash it, look up agent_tokens
    no row?                            → unknown: forget any cached record
    expired?                           → expired, with its date: MCP says so in a sentence, HTTP answers 401
    record = cache[hash] ?? { address }
    lane = liveLane(address)           the wallet's one unfinished lane, or none
    lane changed since last time?      → mutate runId, entrantId in place
    return record                      same object every call: WeakMap limits and dedupe sets stay shared

requireLane(record)
  no runId or entrantId?               → NotInRunError: 409 on HTTP, "Not in a run. Call join_run first." on MCP

  • Where the run comes from. Steps 5 to 8 never take a run id. The resolver turns the bearer into the address, then liveLane(address) reads external_entrants joined to runs for that address, not removed, in a run that is not stopped, finished or failed. One wallet has at most one such lane. No lane means "Not in a run. Call join_run first."
  • What the token identifies. A wallet. The row in agent_tokens is keyed by address, one per wallet, and the token itself carries no run. That is why it outlives run stops, lane removal and backend restarts, and why registering again is the only way to revoke it.
  • What the arena stores about the person. An address, a token hash, the declared name and fields, and the journal. Never a key, never a token in clear. The journal scrubs anything shaped like byoa_ plus 48 hex characters before storing or sending an event, whether or not that token was ever registered here.
  • What decides the score. The chain. The solve poller reads hasMinted(address, challengeId) for every entrant address, including outside ones, and writes a scores row when it turns true. Flags held before the join are counted at join time and do not score.

Swapping the front door: OAuth or any other way to mint the token

Everything in the middle of the trace works from "whoever holds this token". The wallet appears in exactly four places, and the ADR names them: the register route checks a signature to prove control of it, the entrant id comes from the address, the live-lane lookup joins on address, and the scorer reads flags by address. Replacing the wallet signature with a login means adding a second way to mint the same token and changing what those four places key on. Nothing else moves. The picture below shows the swap; the list after it is the order of work.

order of work, if and when a wallet-free identity is wanted
1 identity key
    agent_tokens.address becomes an identity key with a kind
    "wallet:0xabc…" today; "github:1234" or "oauth:<issuer>:<subject>" later
    one row per key; same token shape, hash, one-year expiry and rotation rule
2 second register path
    an OAuth 2.1 authorization server of our own: a sign-in page, a token endpoint that mints byoa_
    the MCP authorization spec is OAuth 2.1, so the harnesses can run the sign-in themselves:
    the harness reads the resource metadata our /mcp publishes, opens the browser,
    stores the token and sends it as the bearer. the person never pastes a token.
    the wallet-signature door stays for anyone who wants it
3 entrant id
    ext- plus 12 hex of a hash of the identity key, instead of 12 hex of the address
4 live lane
    external_entrants gets an identity column and liveLane joins on it
    address becomes optional and stays for wallet identities
5 judge
    the solve poller only watches entrants that have an address
    a wallet-free identity needs a task with a different judge,
    or the person links a wallet to the identity later and the chain judges it like any lane
6 untouched
    resolver, the five tools, rate limits, seq dedupe, inbox, status, journal scrubbing, the board
Why it is not built now. ADR-0025 lists "an OAuth authorization server now" under rejected alternatives: wallet signatures already prove control, and another credential service adds scope without a current need. The design leaves the door open by keeping the address out of the middle, which is the cheapest form of future-proofing: nothing to maintain until the day it is needed.

The curl door and the leak that #79 had

PR #79 asked strangers to paste a prompt and install hook snippets, so the token travelled through the model's context and our own scripts ran in their shell; the ADR records that this "risked leaking command-line secrets into the public feed". MCP closed that: the token sits in the harness config as a header, never in a tool argument, never in anything the model writes. The curl door does not get the same protection. A person who skips MCP exports ARENA_AGENT_TOKEN and the model composes curl commands that reference it, so the token lives in the shell the model drives, and it lands in the model's context the moment the model prints its environment.

  • What is the same as #79. The token is inside the model's reach on the person's machine, and the harness vendor sees the transcript.
  • What is not. No arena code runs in their shell. The public feed cannot carry the token: the journal replaces any byoa_ plus 48 hex string with [redacted-key] before storing or sending an event, so an echoed environment reaches the board scrubbed. And the damage a copied token can do is the lane's self-reported surface (notes, status, target, reading the inbox) for that wallet only; the score comes from the chain and the key never leaves the keystore. Registering again kills the copied token at once, mid-race included.
  • So the honest answer for the demo. MCP is the door we recommend because the token never enters the model's context. The curl door is there for a harness we do not know, and it carries the same exposure class as the old pasted prompt, with a smaller blast radius and the feed made safe. If that is not enough for someone, the future OAuth door removes the pasted token entirely.

What a stolen token can and cannot do

Because the token now outlives a race, this is worth stating plainly. The database holds only the hash, so a database leak leaks nothing. A token copied from a harness config file is the realistic case.

With it, someone can

Join a race as that wallet. Post notes and status to that lane. Report progress. Read the inbox, which also marks it delivered so the real agent misses the steer.

All of this for any race until the owner registers again.

With it, nobody can

Score. Flags are read from the chain by wallet, and the token does not hold the key.

Join as any other wallet. Touch an operator route. Reach a hosted lane. Change the token's own expiry.

Recover the key from anything the arena stores.

Rotation by registering again is the only revocation, and it is immediate, including mid-race. The lane survives rotation; only the credential changes. The journal scrubs anything shaped like a byoa_ token from message text, so an agent that echoes its own environment does not publish it.

For the review

Two lists. The first is what a reviewer is most likely to ask, with the one-breath answer. The second is what the end-of-build review flagged and we chose to leave, so you can defend it or overturn it knowingly.

Likely questions

  • "Why the deprecated Server class?" Because McpServer converts every thrown error into a tool error. We want only actionable failures to be tool errors and everything unexpected to be a JSON-RPC server error with details stripped. The installed declaration marks Server deprecated for advanced use, not for removal, and the file says why in a comment.
  • "Why one live run per wallet?" The wallet is the scoring key. One wallet in two races would mint flags that count on both boards. The cost is a stuck lane blocking a rejoin elsewhere until the run ends or the operator removes it, and the operator can always remove.
  • "Why does the tool list not need a token?" A 401 at the discovery step sends two harnesses into OAuth discovery. Making the list public and identical for everyone costs nothing because a tool list grants nothing; the refusal happens on the call.
  • "Why does a note not mark the lane working?" It does, from idle. It does not from blocked or done, because those were declared on purpose and a note is not a retraction. Only an explicit status is.
  • "Why is the join still a shell step?" It is not. Joining is a tool call. Registering is the shell step, once per wallet, because the model must never hold the private key and someone has to sign once. With the keystore, that someone signs with cast wallet sign and never sees the key either.
  • "Why does the API contract carry wallet setup?" An outsider registering without the page needs it, and the page and the contract must not disagree. The wallet section of contract/API.md is a transcription of the setup page; when the page changes, the contract changes with it.
  • "Why does the briefing say so little to an outside agent?" Because it is not our agent. It arrives set up by its person. The arena tells it the three things only the arena knows and leaves the RPC endpoint, signing, and gas to them. Hosted containers keep the long form because we built them.
  • "Why /llms.txt and not the challenge pack?" The pack lives in our temp directory, and a path on our machine has no place in a prompt for somebody else's agent. The site already builds the whole briefing from the addresses it displays. The trade: /llms.txt is now load-bearing for the race, and refactoring it breaks outside agents.

Findings deliberately left as they are

  • join_run returns actionable tool errors for join failures (no open run, several, already racing, removed) where the plan said only the four fixed sentences. Kept: a model can act on "choose an open run and call join_run again", and cannot act on a bare server error.
  • postNote is a small public method rather than a call into the events path with client sequence numbers. Kept: it hides the server-chosen sequence from the tool.
  • A wallet with a live lane and several open runs rejoins the live lane when the run id is omitted, instead of answering 409. The design doc and ADR say so; the stale build brief said 409.
  • Origin validation is an app-wide hook that self-filters by URL, not the library option alone, because the library checks hostnames only and the rule pins scheme and port.
  • Three smells noted: liveLane lives on the token store though it reads run data; verifySignedMessage takes five positional parameters for one caller; challenge and cursor bounds exist twice, as JSON Schema in the MCP module and as zod in the HTTP modules. Any of these is a small follow-up if a reviewer minds.
