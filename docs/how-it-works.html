How the arena runs a race

Two coding agents work the same practice-puzzle chain, each in its own container, and every step streams to the frontend. This page walks the five flows that make one run happen, straight from the code.

The stack

One Node process runs the whole arena. Fastify serves the HTTP and SSE routes; RunManager owns the run lifecycle and the two drivers. Docker isolates the entrants, one hardened container each, and each container carries the burner's WALLET_ADDRESS, WALLET_PRIVATE_KEY, and ETH_RPC_URL as env. Those burner keys are derived from one funder signature and live only in process memory for the run. SQLite stores events, run and entrant rows, addresses, and scores. A private hardhat or anvil chain at chainId 31337 is the game board. The Vite/React frontend holds no state of its own; it watches the event stream.

The chain hosts only practice puzzles. Each puzzle is a small Solidity contract with an intended solution, like an advent-of-code box. Nothing here is a live system.

What lives in SQLite

SQLite keeps the event journal, run state, entrant addresses, and scores. It never stores the seed signature or burner keys. On startup, chain storage runs DROP TABLE IF EXISTS wallets to destroy keys left by older database files. src/db/schema.ts · src/chain/storage.ts

01

Seed signature and funding

A run walks created → awaiting_signature → preparing → awaiting_funding → ready → running → stopping → finished, and any state can move to failed. Each step is a legal transition, and an illegal one throws. Two of those states wait on a human — one for a signature, one for money — though the local dev profile answers both for itself. src/run-manager.ts · LEGAL_TRANSITIONS

The arena holds no private key at rest. One signature from the funder seeds every burner in the run, so no address can exist before that signature lands — which is why the signing step sits ahead of container prep, not after it.

The lifecycle, state by state

The chainless fake-duel preset skips the seed step outright: it never enters awaiting_signature, and its funding gate returns the moment it is called, so no wallet is ever derived for it.

What the funder sees

The mock frontend ships the reference waiting room. It appears whenever the run sits in awaiting_signature or awaiting_funding, and it is the one screen that needs a human. packages/mock-frontend/src/waiting-room.ts · main.tsx

  • In awaiting_signature the panel prints the run id and the exact typed-data JSON to sign. The browser builds that JSON itself, byte for byte, from the run id and its local chain id — the backend never ships it. A copy button hands it to cast wallet sign --data or another wallet.
  • With an injected wallet present, sign with wallet calls eth_requestAccounts, then eth_signTypedData_v4 with the account first and the JSON string second. MetaMask renders the domain and Seed.runId as a structured prompt. A dismissed prompt arrives as EIP-1193 code 4001 and reads "wallet request rejected", not as a failure.
  • The copy-and-paste fallback stays visible with or without an injected wallet. The paste box tests the signature against /^0x[0-9a-fA-F]{130}$/, the same shape the backend's schema accepts, so a typo never reaches the network.
  • A rejection names the status, never the wallet: 403 says the signature did not come from the wallet this profile funds with, 409 says the run is no longer waiting, 400 says the string is not a signature it can read.
  • Under the panel sits the roster, one row per entrant: entrant id, the full address as a click-to-copy button, and a funding status. Before the signature lands, that middle column reads "address arrives with the signature".
  • In awaiting_funding the panel shrinks to one line — send ETH to each address below — and each roster row flips from waiting to funded with its balance beside it. A top-up to the same address counts, because the gate reads balances rather than transfers.

How the burner is born

Every key in a run is born in one call, the moment the seed is accepted. POST /runs/:id/seed takes {signature} and works only while the run is in awaiting_signature. src/server.ts · src/run-manager.ts · submitSeed

  • The funder signs EIP-712 typed data with domain {name: 'agents-arena', version: '1', chainId}, primary type Seed, and one field: runId: string. There is no verifying contract. The run id gives every run virgin wallets; the domain binds the signature to one chain. src/chain/wallet.ts · seedTypedData
  • canonicalizeSeedSignature runs first. A high-s signature is rejected outright; the rest are re-serialized low-s with v 27 or 28. Every accepted encoding of one signature therefore collapses to one byte string, and one key set.
  • Recovery runs against those canonical bytes. A signature that does not recover to the profile's funderAddress gets a 403 and the run stays put. A post from any other state gets a 409, and so does a second post while the first is still in flight.
  • deriveEntrantKeys then computes each key as keccak256(canonical signature bytes ‖ utf8 entrantId) and takes its address. The keys go into a per-run map in process memory, keyed by run id then entrant id; the function itself returns addresses only.
  • RunManager writes those addresses to entrants.address in one transaction, then appends one wallet.assigned per entrant. If either write throws, it drops the run's keys and fails the seed.

Here is one real run of that derivation: the local profile, runId "1", and the local dev funder — anvil account 0. That account's private key is printed in every anvil banner, so the burner keys below are public arithmetic and guard nothing. They are here to show the shape.

  • recoverTypedDataAddress over that typed data and signature returns 0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266, which is the local profile's funderAddress, so the seed is accepted. Any other signer recovers to some other address and gets a 403.
  • The two addresses go to entrants.address in SQLite. The two keys go only to the in-memory vault, and from there to each container's WALLET_PRIVATE_KEY.
  • Signing that same typed data again returns byte-identical output — the nonce comes from the key and digest, not from randomness (RFC 6979). That is why re-signing next week re-derives these same two wallets and recovers whatever ETH is left in them.
  • The run id reaches the keys only through the typed data the funder signed, which is where run-uniqueness comes from. The chain id changes the signature before derivation, so the same run id on another chain produces other burners.
  • A keccak256 output works as a secp256k1 private key for a dull reason: a private key is only a 256-bit number below the curve order, and a hash hands you 256 high-entropy bits.

What the run emits while it waits

That is the whole vocabulary of the waiting room, and none of it carries key material. The signature lives in the request body and in submitSeed's local variables; no journal row holds it and no code path logs it. The derived keys leave process memory only as container environment variables. So the frontend never learns that a key exists — it learns addresses, from wallet.assigned and from entrants.address in the run snapshot, and that is all it needs.

How the burner gets funded

After both containers prepare, the run moves to awaiting_funding. The funding gate only watches balances on every profile and holds the run until both burners are funded. The composition root runs a separate local-only faucet beside that gate.

  • The watcher awaitFunding starts first and polls every 500 ms. It reads each balance at head − confirmations, not at head. src/chain/funding-watcher.ts
  • On local, runLocalDevFaucet sends 0.1 ETH to each underfunded burner from anvil account 0, then mines enough blocks for the confirmed-balance read. It is wired beside the gate in src/index.ts, not inside it. src/chain/funding-gate.ts
  • On Base, a human funds the displayed addresses. The waiting-room UI carries the prompt, and multisend is the operator's tool of choice. The server never sends Base funds.
  • fundingThresholdEth is 0.05 on local and 0.005 on Base. It only confirms that money arrived; the funder chooses the race stake and can sweep leftovers later. config/chains.json
  • The local timeout is 15 minutes. Base omits fundingTimeoutMs, so it waits until funding, stop, or reset. Every balance change emits funding.balance; the run moves to ready when both balances cross the threshold.

Stop, restart, and the leftover ETH

  • stop drops the run's keys before it touches a container, and teardown drops them again once the drivers settle. After that the process holds nothing derived from the signature. src/run-manager.ts · dropRunKeys
  • A stop during awaiting_signature aborts the waiting start and walks stopping → finished, same as a stop from running. A stop from preparing, awaiting_funding, or ready lands on failed with the reason "stopped by operator before running".
  • A backend restart takes the key map and the in-memory seed waiter with it. A run parked in awaiting_signature is orphaned: the row still reads awaiting_signature, but a seed post now answers 409. Stop that run and create a new one — the backend resumes no pre-terminal run. contract/API.md
  • Money already sent survives all of that. ECDSA signing is deterministic, so the funder signs the same typed data again, canonicalizes it the same way, hashes it with each entrant id, and holds the same keys — offline, with no server in the path. The sweep is the funder's capability, not the arena's. docs/adr/decisions-log.md · ADR-0012
  • The addresses outlive both the keys and the run. entrants.address stays written, and the solve poller reads it to score: a scores row is unique on (run, address, challenge). src/chain/solve-poller.ts
Local signing. The backend signs the seed with the anvil dev key on the local profile, so the normal dev loop stays zero-touch and self-funded. Set ARENA_AUTO_SIGN=false to exercise the real signature flow. Base ships with a zero funderAddress placeholder, which blocks seeding until a real treasury EOA is configured. src/run-manager.ts · config/chains.json

Credentials into each container

Each entrant runs in its own hardened container. Before the container starts, the driver builds a temporary credential directory on the host and mounts it in. Login files go in over a mount; the wallet and the RPC URL go in as environment variables.

codex

  • Makes a fresh temp dir, copies the operator's auth.json in, and writes a config.toml. It pins a model only when the preset names one; a ChatGPT-account login rejects API-only model ids, so the default login stays on its own default. src/adapters/codex.ts · createContainer
  • Mounts that dir at /creds/codex and sets CODEX_HOME to the same path so the CLI finds the login.

opencode

  • Makes a temp dir mounted at /creds/opencode. The OpenRouter key comes from OPENROUTER_API_KEY or the operator's opencode auth.json, and rides in as the OPENROUTER_API_KEY env var. src/adapters/opencode.ts
  • OPENCODE_SERVER_PASSWORD and OPENCODE_PORT get stripped from the container environment before launch. scrubOpenCodeEnvironment

Wallet injection (both harnesses)

  • At prepare time the driver reads the burner from the process-memory map with getWallet and adds WALLET_ADDRESS and WALLET_PRIVATE_KEY to the container env alongside ETH_RPC_URL. The agent signs with cast send --private-key "$WALLET_PRIVATE_KEY".
  • The env is the only copy that leaves the process, and it is the only place a key is ever written down. getWallet returns null on a chainless preset, so those containers get ETH_RPC_URL and no wallet at all. Teardown calls dropRunKeys, and a restart takes the map with it.

Why the container is boxed in

  • CapDrop: ['ALL'] and SecurityOpt: ['no-new-privileges']: no Linux capabilities, no privilege escalation. Never privileged, never mounts the Docker socket. src/runtime/container.ts
  • Bounded resources: PidsLimit 512, Memory 2 GiB, NanoCpus 2. One private bridge network per entrant, and its own credential mount.
  • ExtraHosts: ['host.docker.internal:host-gateway'] lets the container reach the chain running on the host. ETH_RPC_URL points at http://host.docker.internal:8545.
Why not localhost:8545. Inside a container, localhost is the container itself, not the host. The chain runs on the host, so the container reaches it through host.docker.internal, which the host-gateway entry resolves. The opening prompt tells the agent this outright. src/run-manager.ts · buildOpeningPrompt
03

Server-side events and the SSE feed

Every fact in a run is one row in an append-only journal: a log the code only adds to, never edits. The frontend reads that journal live over one SSE stream per run, and a reconnect picks up where it left off with no gap and no duplicate.

SSE is Server-Sent Events: one ordinary HTTP response the server never closes. It keeps appending lines as events happen, and the browser's built-in EventSource reads them live. On a dropped connection EventSource reconnects on its own and resends the last id it saw in a Last-Event-ID header, so the server replays only what the browser missed. That free resume is why SSE fits this one-way feed better than a websocket, with no second protocol to run.

The journal

  • append assigns two numbers in one transaction: a global autoincrement id shared across all runs, and a seq that counts up per (runId, source). src/journal.ts
  • The id is one counter over every run, so inside a single run it can jump when another run writes in between. The seq counts 1, 2, 3… for one (run, source) with no holes. Section 4 leans on that difference.
  • source is the entrant id for a lane event, or the literal 'run' for a run-level event like a state change.
  • After the write, append pushes the event to any live subscriber for that run. after(runId, afterId) reads back every row past a given id, in id order.

The SSE endpoint

  • GET /runs/:id/events resumes from a cursor: it takes the higher of the ?after query and the Last-Event-ID header. src/server.ts · openEventStream
  • Replay then live, with no lost event in the seam: it subscribes first and buffers arriving events in a pending list while it replays history, then sorts the buffer by id and flushes it. send drops anything at or below the last id it wrote, so the overlap never double-sends.
  • It writes each event as id: <n> + data: <json>, and sends a : heartbeat comment every 15 s to hold the connection open.

How the frontend syncs

The frontend folds the event stream into one state object. It dedupes reconnect overlap, flags real data loss, and renders every event type as a line, so the feed never blanks.

Dedupe and gap detection

  • Dedupe runs on the global id. After a reconnect the browser replays a few events it already saw; seenIds recognizes those ids and drops them, so nothing counts twice. Returning the same state object lets React skip a re-render. packages/mock-frontend/src/feed-projection.ts
  • Loss detection runs on seq, not id, because id can skip for an innocent reason (another run wrote in between) while a source's seq never does. If opencode-1 jumps from seq 4 to seq 7, two events are gone: the UI records a FeedGap and shows a warning instead of a silently wrong race.
  • This is why both numbers exist. Without the id check a wifi blip could double-count a minted flag; without the seq check it could hide one, and the scoreboard would lie.

Lanes and the wallet header

  • eventsForSource filters the feed by source === entrantId, so each lane shows only its own entrant's events. Run-level events use the 'run' source.
  • describeEvent renders a one-line summary for every known type, and any type the UI doesn't know falls through to rawFallback, which prints the raw payload. The feed never shows a blank row.
  • deriveLaneWallet folds a lane's events into its wallet header. The address starts from the run snapshot, then wallet.assigned and funding.balance override it; balance and the funded flag come from the latest funding.balance. awaitingFunds is true while the run is awaiting_funding and this lane is not funded yet.
  • deriveWaitingRoom runs the same fold over every entrant to build the pre-race roster, and labels each row pending with no address, waiting with an address and no funds, funded past the threshold. The whole wallet story the UI can tell is two payload fields — an address and a balance. It has no way to ask whether a key exists, and never does.
05

How steer works

An operator can inject a free-text turn into a live agent mid-race. If the agent is mid-turn, the steer waits in a queue and lands when the turn ends. If it's idle, it resumes the same harness session inside the same container.

  • POST /runs/:id/entrants/:entrantId/steer takes free text, replies 202, and calls RunManager.steer, which looks up the entrant and calls the driver. src/server.ts · src/run-manager.ts
  • A degraded or stopping entrant rejects the steer: the driver throws EntrantUnavailableError, and the caller records the miss on the lane. src/adapters/harness-driver.ts · steer
  • If a turn is in flight, the text goes onto queuedSteers and the call returns. When the turn ends, finishTurn shifts one queued steer and starts it as a resume.
  • An idle entrant resumes right away. The resume runs codex exec … resume <sessionId> or opencode run -s <sessionId> in the same container, so the agent keeps its context. A resume before the harness has reported a session id is rejected the same way; the entrant steers normally once the opening turn reports one.
  • Each resume appends an entrant.steered event to that entrant's lane, so the steer shows up in the feed.
